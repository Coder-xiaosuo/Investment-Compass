## 1. 结论摘要

对 `investment_compass` 全库 42 张表逐表取证，确认 **21 张为异种产品遗留、零代码引用**，已通过 `V016` 迁移删除。**表数 42 → 21**。

| 项 | 值 |
|---|---|
| 删除表数 | 21（全部 0 行） |
| 保留表数 | 21（16 业务 + 4 LangGraph checkpoint + 1 运维待决） |
| 删除表占用 | 992 KB / 全库 99,440 KB = **1.0%** |
| 保留表数据 | CHECKSUM 逐表比对，**零变化** |
| 代码影响 | Python 13 个模块导入正常；Java 14 个接口全部通过 |

> **必须说明**：本次收益**几乎不是磁盘空间**（仅省 1.0%），而是**运维与认知成本**——消除 `watchlist` / `watchlists` / `watchlists_v2`、`positions` / `positions_v2` 这类同名歧义，备份不再携带无关 schema，并使 `models.py` 与真实库一致。若目标是省磁盘，本方向收益有限。

## 2. 根因

`schema` 的混乱源自一个**产品边界问题**：

本库由 FinAgentOS 项目的备份迁移而来（[docker-compose.mysql.yml](../../docker-compose.mysql.yml#L22) 通过 `docker-entrypoint-initdb.d` 挂载备份导入）。而 **FinAgentOS 与 Investment-Compass 是两套设计取向相反的产品**：

| | FinAgentOS | Investment-Compass |
|---|---|---|
| 定位 | 金融多 Agent 模拟**交易**操作系统 | A 股**投研分析**助手 |
| 核心表 | orders / positions / audit_chain / factor_library | **market_data / stock_metadata** |
| 对行情数据的态度 | `finagentos_schema_v2.sql` 明确标注 **「market_data 废弃，AkShare + Parquet 存储」** | market_data 是**核心表**（16 万行，全项目读路径中心） |

即：FinAgentOS 主动**废弃**的两张表，恰是本项目的根基。这 21 张 trading 平台脚手架表随备份一并迁入，从未被清理。

## 3. 排查方法与判据

对 42 张表逐表执行 6 项检查，**全部不满足才判定可删**：

1. **精确行数** —— 注意 `information_schema.TABLE_ROWS` 是估算值不可靠（`watchlist` 显示 0 实际 3 行），必须 `COUNT(*)`
2. **Python 引用** —— 在 `services/`、`agents/`、`main.py` 中检索表名（排除 `models.py` 的 ORM 声明）
3. **Java 引用** —— 在 `java-backend/src` 检索表名与 Mapper
4. **ORM 实例化** —— 检索 `User(...)` / `Order(...)` 等构造调用
5. **外键依赖** —— 查询 `information_schema.KEY_COLUMN_USAGE`
6. **是否会被重建** —— 检索 `Base.metadata.create_all()` 调用点

关键排除项：

- **`checkpoint*` 4 张不是遗留表**。初看像技术债，实为 [main_agent.py#L23](../../python-service/agents/main_agent.py#L23) 使用的 LangGraph MySQL checkpointer（HITL 线程状态），现有 1640 条 checkpoint 在用 —— **必须保留**。
- **`create_all()` 仅在 2 个测试脚本中调用**（`test_news_integration.py` / `test_advisory_agent.py`），生产启动不会重建，故删除后不会"长回来"。
- **全库唯一外键是 `message → conversation`**，与待删表无关，删除**无依赖顺序问题**。

## 5. 实施内容

### 5.1 迁移脚本

`sql/V016__drop_finagentos_legacy_tables.sql` —— 21 条 `DROP TABLE IF EXISTS`，含完整回滚说明。

### 5.2 清理 `models.py`

该文件头部原标注「FinAgentOS — SQLAlchemy ORM Models」，含 27 个 ORM 类。实测**仅 3 个类被运行时导入**：`DecisionCard`（技术分析 Agent）、`StockNews` / `ResearchReport`（`news_service`）。

- 移除 19 个对应已删表的类（`User` / `Workspace` / `Order` / `Position` / `AuditChain` / `FactorLibrary` 等）
- 同时移除 `StockMetadata` / `MarketData` / `Conversation` / `Message` / `AgentThread` —— 这些表**保留**，但全项目通过原生 SQL 访问，ORM 声明从未使用；且其声明**已与真实库脱节**（如 `MarketData` 仍写着 V015 之前的旧索引 `uk_md_symbol_date_tf`，会成为陷阱）
- 结果：27 个类 → **3 个**，文件 477 行 → 112 行

### 5.3 整理 `sql/`（按"仅保留收敛后的 SQL"要求）

| 动作 | 文件 | 理由 |
|---|---|---|
| **新增** | `sql/schema.sql` | 权威基线快照，由真实库 `mysqldump --no-data` 导出，21 张表 |
| **新增** | `sql/V016__drop_finagentos_legacy_tables.sql` | 本次变更的迁移记录 |
| **删除** | `sql/finagentos_mysql_schema.sql` | 异种产品 schema，含 21 张已删表 |
| **删除** | `sql/finagentos_schema_v2.sql` | 同上；且其设计前提（market_data 废弃）与本项目相反 |
| 保留 | `V002` ~ `V015` | 迁移历史即审计轨迹 |

**为什么要新增基线**：`sql/` 迁移链已与真实库脱节，实证两处——

1. `watchlist` 实际含 `symbol_name` 列，但 **V003 / V006 均未定义**该列（由备份 dumps 带入）
2. `V006__create_watchlist.sql` 与 `V003` **同名表、不同结构**；因 V003 先执行且 V006 用 `CREATE TABLE IF NOT EXISTS`，V006 从未生效，属惰性且误导的文件

基线文件已在 Header 中记录这两处偏差及 `models.py` 的处置，供审计追溯。两个 FinAgentOS 文件均在 git 版本控制中（初始提交 `93cb757`），DDL 可完整回溯；且删除时全部 0 行，无数据损失。

> **`V006` 未删除**：它产生的是 `watchlist`（保留表），不在本次批准的「产生已删表的源文件」范围内，故仅记录为遗留项（§7.2），不做处理。

## 7. 顺带发现（**均为既有问题，与本轮无关，未修改**）

### 7.1 【阻断级】`main_agent` 无法导入 —— 对话/Agent 功能不可用

```
ImportError: cannot import name 'deepseek_model_kwargs' from 'shared.config'
```

`agents/main_agent.py:30` 导入该函数，但 `shared/config.py` **从未定义过它**。

经 `git log -S` 确认：**自初始开源提交 `93cb757` 起即如此**，非本轮引入（`config.py` 与 `main_agent.py` 本次均未改动）。

影响：`chat_service` 在 3 处懒加载 `agents.main_agent`，因此 `/api/chat/*` 与 `/api/chat/{id}/resume` 等**对话类接口在调用时会失败**；应用本身可启动（非法导入不阻断 FastAPI 启动），故此前未被发现。

> 建议优先修复 —— 这是当前唯一影响功能可用性的缺陷。

### 7.2 【可维护性】`V006__create_watchlist.sql` 与 `V003` 冲突

同名表、不同结构，且从未生效（见 §5.3）。保留会造成"迁移链里到底哪个是真的"的困惑。建议删除或标注为 superseded。

### 7.3 【待决】`data_quality_issue` 有读接口无生产者

Java 侧 `/monitor/quality-issues`（[MonitorMapper#L55](../../java-backend/src/main/java/com/xiaosuo/investmentcompass/mapper/MonitorMapper.java#L55)）读取该表，[#L74](../../java-backend/src/main/java/com/xiaosuo/investmentcompass/mapper/MonitorMapper.java#L74) 更新其 status；但全库无任何 INSERT —— Python 侧 `data_filter` 发现的数据质量问题时只打日志，未落库（[01-总体架构](./01-总体架构.md#L100) 的「Python 写入」是设计意图，未实现）。

两条路径：**补生产者**（让 `data_filter` 落库，功能即完整），或**删表 + 移除 Java 端点**。建议前者——质量问题落库对数据治理有实际价值。

### 7.4 【依赖】`langgraph-checkpoint-redis` 与 MySQL checkpointer 并存

`requirements.txt` 同时引入 `langgraph-checkpoint-mysql` 与 `langgraph-checkpoint-redis`，但代码实际使用 `AIOMySQLSaver`。Redis 版依赖疑为冗余（非表结构问题，故未处理）。
