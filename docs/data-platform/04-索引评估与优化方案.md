# market_data 索引评估与优化方案

> 文档系列：数据中台（`docs/data-platform/`）
> 本文档：04-索引评估与优化方案
> 关联文档：[01-总体架构](./01-总体架构.md) / [02-数据写入链路](./02-数据写入链路.md) / [03-数据读取规范](./03-数据读取规范.md)

## 1. 定位与范围

本文档回答一个问题：**`market_data`（K 线）应当建立哪些索引**。

范围：`market_data` 单表的索引结构（保留 / 新增 / 删除）及为避免性能回退所必需的配套查询修正。
不涉及：缓存层（另有 Redis 版本号失效方案）、分区、读写分离、分钟线工程化落地。

## 2. 现状

### 2.1 数据规模

| 项 | 值 |
|---|---|
| 总行数 | 160,442 |
| 标的数 | 744 |
| 日期范围 | 2020-01-02 ~ 2026-09-14 |
| `timeframe='1d'` | 160,439 |
| `timeframe='D'` | 3（脏数据，见 §7.4） |

> 注：规划中的全量重建目标为 5,527 标的 × ~1,600 交易日 ≈ **880 万行**，是当前规模的 55 倍。

### 2.2 现有索引

| 索引 | 列 | 判定 |
|---|---|---|
| `PRIMARY` | (id) | 保留（InnoDB 聚簇索引必需） |
| `uk_md_symbol_date_tf` | (symbol, **trade_date**, timeframe) | **列序错误**，改列序 |
| `idx_md_symbol` | (symbol) | **删除**（冗余） |
| `idx_md_trade_date` | (trade_date) | **替换**为 (timeframe, trade_date, symbol) |
| `idx_md_fetched` | (fetched_at) | **删除**（无引用） |

## 3. 查询形态盘点

`market_data` 的读取方共 2 个语言、9 处入口。按访问维度归类：

| # | 调用方 | 访问维度 | 排序/范围 |
|---|---|---|---|
| Q1 | `StockService.loadBars`（`/stock/kline` 主导路径） | symbol + timeframe | trade_date DESC LIMIT n |
| Q2 | `StockService.loadBars`（日期区间） | symbol + timeframe | trade_date BETWEEN |
| Q3 | `MonitorMapper.selectStockLatestBySymbol` | symbol + timeframe | trade_date DESC LIMIT 1 |
| Q4 | `StockService.getStockDetail` | symbol + timeframe | trade_date DESC LIMIT 2 |
| Q5 | `MarketDataMapper.selectLatestQuote` | symbol **IN** + timeframe | MAX(trade_date) 分组 |
| Q6 | `MarketBoardService.getRanking` ① | timeframe（**无 symbol**） | trade_date DESC LIMIT 1 |
| Q7 | `MarketBoardService.getRanking` ② | trade_date = + timeframe | pct_chg 排序 |
| Q8 | `MonitorMapper.selectOverview` / `selectCoverageSummary` | timeframe | 全表聚合 |
| Q9 | `kline_coverage_service._load_actual_dates` | symbol + timeframe | — |
| Q10 | `get_latest_market_date`（Python 增量热路径） | symbol（**无 timeframe**） | MAX(trade_date) |
| Q11 | `get_realtime_quote`（Python） | symbol（**无 timeframe**） | trade_date DESC LIMIT 1 + 自连接 |
| Q12 | `get_kline_history`（Python） | symbol + `LOWER(timeframe)` | trade_date DESC LIMIT n |
| Q13 | `backtest_service` ×3 | symbol（OR LIKE）+ timeframe + closed | trade_date 范围 + LIMIT |
| Q14 | `experience_loop_service` / `technical_analysis_agent` / `backfill_experiences` | symbol + timeframe + closed | trade_date 范围 + LIMIT |

**归纳**：所有高频查询都落在两个维度上——
① **单标的定向读**（Q1~Q5、Q9~Q14）：`symbol` + `timeframe` 等值；
② **跨标的按日读**（Q6~Q8）：`timeframe` + `trade_date`。

现有索引的问题是①的**列序与查询模式相反**：查询按 `timeframe` 等值过滤、按 `trade_date` 排序，而索引把 `trade_date` 放在 `timeframe` 之前。导致执行计划变为"先扫该标的所有周期行，再逐行过滤 timeframe"。

## 4. 测试方法与结果

### 4.1 方法

因当前库仅 16 万行且**只有日线**，索引列序的缺陷被规模掩盖。故构造对照表实测：

- 规模：1,500 标的 × 1,600 日线 ≈ **240 万行**，另加 10 标的的分钟线（24,000 行）以复现"同标的混合周期"
- 表 A = 现列序 `(symbol, trade_date, timeframe)` + 其余 3 索引
- 表 B = 新列序 `(symbol, timeframe, trade_date)` + `(timeframe, trade_date, symbol)`
- 两组均为非唯一索引（唯一键装不下分钟线，见 §7.2，此处只隔离"列序"变量）
- 度量：`EXPLAIN ANALYZE` 实际耗时与实际扫描行数

### 4.2 结果

| 场景 | 表 A（现状） | 表 B（新列序） | 变化 |
|---|---|---|---|
| Q1 单标的日线 120 根 | 15.3 ms / 扫 1,600 行 | **0.30 ms** | **51×** |
| Q1（分钟线密集的标的，24 万行混合表） | 42.8 ms / 扫 38,760 行 | **0.15 ms / 扫 120 行** | **287×** |
| Q6 排行榜取最新交易日 | 73.4 ms / 扫 24,001 行 | **1.12 ms** | **66×** |
| Q8 监控总览（非覆盖） | 1,802 ms | 2,086 ms | 略差 |
| Q8 监控总览（覆盖索引） | 1,802 ms | **924 ms** | **2×** |
| Q10 单标的 MAX(trade_date) | 即时 | 7.75 ms → 补 timeframe 后**即时** | 需配套修复 |
| Q11 实时行情（仅 symbol） | 0.52 ms | 52.7 ms → 补 timeframe 后 **1.01 ms** | 需配套修复 |
| Q5 selectLatestQuote | 1,794 ms（全表扫） | 1,614 ms（全表扫） | 无改善（另有问题，见 §7.3） |

### 4.3 关键结论

1. **列序是核心问题，不是索引数量**。表 A 的计划形如 `Index lookup(symbol=?) → Filter(timeframe='1d')`，其成本取决于**单标的拥有的行数**（分钟线进来后激增），与全表规模无关，**不会随数据增长被摊薄**。表 B 为 `Index lookup(symbol=?, timeframe=?)`，成本 O(limit)。

2. **`idx_md_trade_date` 并非无用**（此处修正了初步判断）。Q6 的 `WHERE timeframe='1d' ORDER BY trade_date DESC LIMIT 1` 无 symbol 条件，必须靠跨标的索引。但 `(timeframe, trade_date, symbol)` 比 `(trade_date)` 更好：实测 1.12 ms vs 73.4 ms，因它直接定位到 `1d` 分区取末行，无需跳过其它周期的更新日期。

3. **`(timeframe, trade_date, symbol)` 需含 `symbol` 才覆盖** Q8。非覆盖版 2,086 ms，覆盖版 **924 ms**（`COUNT(DISTINCT symbol)` 免回表）。

4. **`idx_md_symbol` 是冗余的**：它是 `uk_md_symbol_date_tf` 的严格前缀列，全部 EXPLAIN 中优化器均选择后者，从不使用它。

5. **`idx_md_fetched` 无任何引用**：按 SQL 指纹检索，引用 `market_data.fetched_at` 的语句数 = **0**。`fetched_at` 仅由 `ON UPDATE CURRENT_TIMESTAMP` 自动维护，无需索引支撑。

6. **写密集表的索引开销**：`market_data` 每次 upsert 都要维护全部二级索引。全量重建 880 万行时，索引维护是写放大的主要来源，由 4 个二级索引降至 2 个是本方案的直接收益。

## 5. 方案

### 5.1 目标索引结构

```sql
ALTER TABLE market_data
  DROP INDEX uk_md_symbol_date_tf,
  DROP INDEX idx_md_symbol,
  DROP INDEX idx_md_trade_date,
  DROP INDEX idx_md_fetched,
  ADD UNIQUE KEY uk_md_symbol_tf_date (symbol, timeframe, trade_date),
  ADD INDEX idx_md_tf_date (timeframe, trade_date, symbol);
```

最终 3 个索引（1 聚簇 + 2 二级）：`PRIMARY(id)` / `uk_md_symbol_tf_date` / `idx_md_tf_date`。

`uk_md_symbol_tf_date` 必须保持 **UNIQUE**——`upsert_market_data` 的 `ON DUPLICATE KEY UPDATE` 依赖它实现幂等，改为普通索引会导致重复写入。

### 5.2 配套代码修复（必需，否则回退）

列序调整会让"仅按 symbol 定位"的查询失去免费的排序/MinMax 优化，以下 5 处必须同步修改：

| # | 位置 | 修改 | 不修改的后果 |
|---|---|---|---|
| 1 | `market_data_service.get_latest_market_date` | 补 `AND timeframe='1d'` | 7.75 ms（原 0.001 ms） |
| 2 | `market_data_service.get_realtime_quote`（m1） | 补 `AND timeframe='1d'` | 52.7 ms（原 0.52 ms） |
| 3 | `market_data_service.get_realtime_quote`（m2 自连接） | 补 `AND timeframe='1d'` | 同上 |
| 4 | `market_data_service.get_kline_history` | 去 `LOWER(timeframe)` | 210 ms（改为等值后 0.97 ms） |
| 5 | `technical_analysis_agent` | 去 `LOWER(timeframe)` | 同上 |

**关于第 4/5 项**：表 collation 为 `utf8mb4_0900_ai_ci`（大小写不敏感），`timeframe='1d'` 本身即匹配 `'1D'`，`LOWER()` 是多余包装，却使索引无法用于等值定位。去掉后语义**完全等价**（脏数据 `'D'` 在两种写法下均不匹配 `'1d'`）。

**关于第 2/3 项**：`get_realtime_quote` 原本未限定周期，会读到 `'D'` 脏行；补 `timeframe='1d'` 同时修正了该语义问题。

### 5.3 验证方法

1. 应用迁移后 `SHOW INDEX` 确认索引结构
2. 对 §3 全部 14 类查询重跑 `EXPLAIN ANALYZE`，确认均走索引、无全表扫描回退
3. 端到端：重启 Java 侧请求 `/stock/kline`、`/market/ranking`、`/monitor/overview`，核对返回结果与迁移前一致
4. 一致性：`kline_coverage.actual_days` 与 `market_data` 实到行数仍全表一致

### 5.4 回滚

```sql
ALTER TABLE market_data
  DROP INDEX uk_md_symbol_tf_date,
  DROP INDEX idx_md_tf_date,
  ADD UNIQUE KEY uk_md_symbol_date_tf (symbol, trade_date, timeframe),
  ADD INDEX idx_md_symbol (symbol),
  ADD INDEX idx_md_trade_date (trade_date),
  ADD INDEX idx_md_fetched (fetched_at);
```

索引变更不改变数据，回滚无数据风险。

## 7. 本轮范围外（已发现，建议后续处理）

### 7.1 排行榜等查询的正确性前置

无。索引变更不改变任何查询结果集，仅改变访问路径。

### 7.2 【数据正确性】唯一键无法承载分钟线

`UNIQUE (symbol, [trade_date|timeframe], timeframe|trade_date)` 中，**同一天的多根分钟线共享键值**。实测插入 3 根同日 `1m` 行：

```
插入 3 根 → 实际留存 1 行（ts_open=3000，即最后写入者）
```

即一旦开始拉分钟线，会**静默丢弃 239/240 的数据**，且无任何报错。修复方向是唯一键含 `ts_open`（实测 `(symbol, timeframe, ts_open)` 可正常容纳），但受 §7.3 阻塞。

### 7.3 【数据质量】`ts_open` 存在两套约定，阻塞 §7.2

全表核查发现 `ts_open` **不是 `trade_date` 的严格函数**：

| 现象 | 行数 | 说明 |
|---|---|---|
| 北京零点约定（= UTC 前一日 16:00） | 146 | `600519`，2025-12-10 ~ 2026-08-07 |
| UTC 零点约定 | 其余 | — |
| `ts_open` 为**秒**（非毫秒，缺 ×1000） | 3 | `000001`，`timeframe='D'` |

当前 0 冲突，是因为 upsert 命中旧键时会**改写** `ts_open`。一旦把 `ts_open` 纳入唯一键，同一 `(symbol, trade_date)` 遇到另一套约定将**插入重复日线**，进而使周线聚合成交量翻倍、`limit` 窗口错位。故须先统一约定再动该键。

### 7.4 【数据质量】3 行脏数据

`timeframe='D'`（大写且非 `'1d'`）共 3 行：`000001` @ 2024-01-02 ~ 2024-01-04，`ts_open` 且为秒精度。它们不匹配任何 `'1d'` 查询，长期是"查不到但占索引"的死行。

### 7.5 【性能】selectLatestQuote 是全表扫描

`MarketDataMapper.selectLatestQuote` 使用 `WHERE (symbol, trade_date) IN (SELECT symbol, MAX(trade_date) ...)`。实测在 240 万行规模下为**全表扫描**（1,794 ms），且补齐 `timeframe='1d'` 亦无法走索引（tuple IN 子查询被物化）。

改写为 JOIN 后实测 **0.5 ms**：

```sql
SELECT m.symbol, m.trade_date, m.close
FROM market_data m
JOIN (SELECT symbol, MAX(trade_date) AS md
      FROM market_data WHERE timeframe='1d' AND symbol IN (...)
      GROUP BY symbol) x
  ON m.symbol = x.symbol AND m.trade_date = x.md AND m.timeframe = '1d'
```

该查询被自选股、大盘看板、行情列表共同使用，属热点路径。当前 16 万行下仍走覆盖索引（未暴露），880 万行时会成为瓶颈。**与本次索引变更无关，故未纳入本轮实施。**

### 7.6 【性能】backtest 的 `OR symbol LIKE`

`backtest_service` 三处使用 `(symbol = :code OR symbol LIKE :code.%)`，该 OR 使排序无法被索引满足（需 filesort）。已确认全库 `symbol` 均为纯 6 位、无后缀（744 个 distinct，带 `.` 者 0），该 OR 属历史防御。去掉可消除排序。属代码层优化，非索引问题。
