# 最新行情查询（selectLatestQuote）优化报告

> 文档系列：数据中台（`docs/data-platform/`）
> 本文档：05-最新行情查询优化报告
> 关联文档：[04-索引评估与优化方案](./04-索引评估与优化方案.md) / [03-数据读取规范](./03-数据读取规范.md)

## 1. 结论摘要

`MarketDataMapper.selectLatestQuote` 原实现使用 `(symbol, trade_date) IN (子查询)`，其 tuple IN 子查询会被 MySQL 物化成派生表，导致**对外层 `market_data` 全表扫描**，且无法通过任何索引改善。改写为 `JOIN` 后，同一查询转为**派生表覆盖索引 skip scan + 外层单行索引定位**。

实测（320 万行规模）：

| 写法 | 4 个标的 | 50 个标的 | 执行计划 |
|---|---|---|---|
| 原 tuple IN | 1,915 ms | 1,979 ms | **主表全表扫描** |
| 改 JOIN | **0.077 ms** | **0.472 ms** | 索引 skip scan + 单行定位 |

> 该查询被大盘指数、自选股列表、批量行情三个热点接口共用，属高频读路径。当前库仅 16 万行，问题被规模掩盖（123 ms）；按规划重建至 880 万行后，将线性放大至秒级。

## 2. 问题定位

### 2.1 关键判定：与 V015 索引变更无关

在 [04-索引评估与优化方案](./04-索引评估与优化方案.md) 的排查过程中，此项曾被列为"与索引变更无关"的独立问题。为排除"V015 导致回退"的可能，做了**同数据、双索引**的对照实验（真实 16 万行，分别建旧/新索引两表）：

| 索引 | 原 tuple IN 查询 | 是否主表全扫 |
|---|---|---|
| 旧索引 `(symbol,trade_date,timeframe)` 等 | 101 ms | **是** |
| 新索引 `(symbol,timeframe,trade_date)` 等 | 96.2 ms | **是** |

**结论**：全表扫描由查询写法本身决定，与索引列序无关。V015 既未引入、也未修复该问题。

### 2.2 根因

MySQL 对 `WHERE (a, b) IN (SELECT ...)` 的处理方式是将子查询**物化为派生表并自动去重**（计划中可见 `Materialize with deduplication` + `auto_distinct_key`），随后外层条件退化为逐行探测：

```
-> Filter: <in_optimizer>((symbol,trade_date) IN (select #2))   rows=159,604
    -> Table scan on market_data            ← 全表扫描，159,604 行
    -> Select #2 (subquery in condition; run only once)
        -> Materialize with deduplication   ← 子查询本身很快（skip scan，4 行）
```

子查询部分本身效率很高（覆盖索引 skip scan，实测 0.7 ms），**瓶颈完全在外层的物化探测**——它对主表每一行都要做一次派生表查找。

这也是为什么该写法无法通过"补索引"解决：无论外层走哪个索引，`in_optimizer` 都会退化为全表扫描。

## 3. 修复方案

### 3.1 SQL 改写

```sql
-- 原实现：外层无 timeframe 限定，tuple IN 触发物化
SELECT symbol, trade_date AS tradeDate, ...
FROM market_data
WHERE (symbol, trade_date) IN (
  SELECT symbol, MAX(trade_date) FROM market_data
  WHERE timeframe = '1d' AND symbol IN (...)
  GROUP BY symbol
) ORDER BY symbol ASC

-- 修复后：显式 JOIN，派生表只含 (symbol, 最新日期)
SELECT m.symbol, m.trade_date AS tradeDate, m.timeframe, m.ts_open AS tsOpen,
       m.open, m.high, m.low, m.close, m.volume, m.amount, m.pct_chg AS pctChg, m.closed
FROM market_data m
JOIN (
  SELECT symbol, MAX(trade_date) AS max_trade_date
  FROM market_data
  WHERE timeframe = '1d' AND symbol IN (...)
  GROUP BY symbol
) latest
  ON m.symbol = latest.symbol
  AND m.timeframe = '1d'
  AND m.trade_date = latest.max_trade_date
ORDER BY m.symbol ASC
```

改写后计划：

```
-> Nested loop inner join
    -> Materialize                                  ← 派生表仅 4 行
        -> Covering index skip scan for grouping    ← 命中 uk_md_symbol_tf_date，不回表
    -> Single-row index lookup on m using uk_md_symbol_tf_date   ← 单行定位，全程走索引
       (symbol = l.symbol, timeframe = '1d', trade_date = l.max_trade_date)
```

### 3.2 附带修正：同标的重负

原实现外层**未限定 `timeframe`**，而派生表的 `MAX(trade_date)` 只来自 `'1d'` 行。因此若某标的在"其最新日线交易日"上还存在其它周期行，外层 tuple IN 会同时匹配这些行，导致**同一 symbol 返回多行**。

构造验证（在 `000001` 的最新日线日 `2026-08-07` 插入一行 `timeframe='D'`）：

```
旧查询返回 5 行：
   000001  2026-08-07  11.190   ← 正确的日线
   000001  2026-08-07  99.000   ← 脏行（'D'）造成重负
   300750  2026-07-17  360.000
   600519  2026-09-14  1277.960
   601899  2026-07-17  28.360
新查询返回 4 行（显式 timeframe='1d'）：同标的重负消失
```

**影响评估**：调用方对重复行的处理不一致——
- `WatchlistService` 用 `Collectors.toMap(..., (a,b)->a)`，重复行被静默吞掉（掩盖了问题）；
- `MarketBoardService.getIndices` 直接 `list.stream().map()`，重复行会**输出两个同名指数**；
- `StockService.getLatestQuote` 同理，会产生重复条目。

新写法从查询层面消除了该分支。当前库中恰好无标的中招（`'D'` 脏行落在 2024-01-02~04，不是任何标的的最新日线日），故线上未暴露。

## 4. 验证结果

### 4.1 结果等价性

真实库上新旧写法逐字节比对：

```
symbols=4   md5 一致  (82c534bf134495d087c4e6d43671fe3f)
symbols=50  md5 一致  (e3d090a223dcdecce14da1ef5e360d82)
```

### 4.2 执行计划与耗时

真实库（160,442 行）：

| 写法 | 耗时 | 主表全扫 |
|---|---|---|
| 原 tuple IN | 123 ms | 1 处（159,604 行） |
| 改 JOIN | 0.347 ms | 0 处 |

对照表（3,200,000 行 = 2,000 标的 × 1,600 日线，3 轮取最小）：

| 组合 | 4 标的 | 50 标的 | 计划特征 |
|---|---|---|---|
| 旧索引 + 旧查询 | 1,915 ms | 1,979 ms | 主表全扫 |
| 新索引 + 旧查询 | 1,826 ms | 1,962 ms | 主表全扫 |
| **新索引 + 新查询** | **0.077 ms** | **0.472 ms** | 单行索引定位 |
| 旧索引 + 新查询 | 2.21 ms | — | 单行索引定位 |

**两点值得注意**：
1. 修复**不依赖** V015——在旧索引下新查询也已从 1,915 ms 降至 2.21 ms（约 870×）；
2. 但两者**协同**更佳——新索引下进一步降至 0.077 ms（再快 29×），因派生表可用 `Covering index skip scan for grouping` 完全避免回表。

### 4.3 端到端

应用启动后，三个调用方接口全部通过，且返回值与库内一致：

| 调用方 | 接口 | 结果 |
|---|---|---|
| `MarketBoardService.getIndices` | `GET /market/indices` | code=0 |
| `WatchlistService.list` | `GET /watchlist/list` | code=0，3 只自选股（含名称联动） |
| `StockService.getLatestQuote` | `GET /stock/quote?symbols=...` | code=0，3 条 |

交叉核对：`600519 / 000001 / 300750` 的接口 `close` 与库内最新日线 `close` **完全一致**。

## 5. 影响面

单文件改动，无接口签名变化：

| 项 | 内容 |
|---|---|
| 文件 | `java-backend/.../mapper/MarketDataMapper.java` |
| 方法 | `selectLatestQuote`（SQL 改写 + Javadoc 更新） |
| 调用方 | 3 处，均无需修改（返回类型、字段别名、排序均保持） |
| 前端契约 | 无变化 |

## 6. 遗留与建议

1. **`'D'` 脏数据未清理**：3 行 `timeframe='D'`（`000001` @ 2024-01-02~04，`ts_open` 且为秒精度）仍存于库中，不匹配任何 `'1d'` 查询。建议在后续数据清理中删除（见 04 文档 §7.4）。
2. **同类写法排查**：`MonitorMapper.selectMissingSymbols` 等使用 `LEFT JOIN ... IS NULL`，无此问题；但建议后续新增"取每组最新一条"类查询时统一用 JOIN，不用 tuple IN。
3. **`symbols` 为空时**：MyBatis `foreach` 会生成 `IN ()` 导致 SQL 语法错误。三个调用方均已前置非空判断（`WatchlistService` 显式判空、`MarketBoardService` 传常量、`StockService.getLatestQuote` 抛参数异常），故未加固；如后续新增调用方需注意。
